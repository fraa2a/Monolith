## Changes

| Finding | Change | Remaining limits |
| --- | --- | --- |
| O01: partial component replacement | Extract and validate all payloads before shutdown. Copy their files into one app-local transaction, sync staged files and a bounded journal, retain original files, and restore the whole plan after a placement failure. An interrupted prepared journal is recovered before the next updater check. Recovery can resume after a partial restoration. Committed journals are cleaned without rollback. | Multi-file replacement is recoverable, not instantaneously atomic. Recovery requires a runnable updater; interruption between parking and placing its executable can require launching a retained updater or reinstalling. Real power-loss durability and a comprehensive Windows fault matrix remain unverified. |
| O02: premature versions and ignored relaunch errors | Include `components.json` last in the same rollback plan as engine, UI and updater files. Read the updater's installed version resource rather than the running process's old build version. Report preparation, metadata, recovery and engine spawn errors. Restart a previously running engine after successful rollback, and report restart failure after a committed update. | Process spawn does not prove engine readiness or successful DLL loading. A full installer/runtime smoke test remains required. |

The journal records relative paths and old/new SHA256 values. Recovery rejects malformed journals, duplicate case aliases, Windows reserved names and observed links/reparse points. It refuses to overwrite unexpectedly changed installed files. Hash checks and path inspection do not establish stable file identity against concurrent external filesystem changes. O05 remains open.

Only planned files are replaced. Unrelated installed files are retained, including user data. Obsolete component files are not automatically deleted. Transaction cleanup is retried on the next updater launch when a parked loaded binary prevents deletion. A new update is refused while those files remain in use.

Updater version advances to 1.0.2 in Cargo, its lockfile and Tauri configuration. Engine and UI versions are unchanged. No signing protocol, dependency, installer publication or release tag changes are included.

## Verification

- `cargo test --locked --manifest-path tests/rust/Cargo.toml`: 14 tests pass on Linux. Eight install regressions exercise interruption after each of nine file moves, late metadata failure, repeat recovery, foreign-file preservation, abort, committed-journal recovery, incomplete preparation, aliases and linked destinations. The six existing tests also pass.
- `cargo check --locked --tests --no-default-features --target x86_64-pc-windows-msvc --manifest-path tests/rust/Cargo.toml`: passes. This type-checks the Windows file operations and Windows-only loaded-updater test; it neither links nor executes the Tauri host.
- `git diff --check`, the repository text policy and focused Rust formatting checks pass.
- Windows execution passed on code commit `dd922544406e309943f7aea646cca70992a22fc0`: [recovery job 113110828408](https://github.com/fraa2a/Monolith/actions/runs/37715473818/job/113110828408), 11 tests passed, zero failed. The one ignored helper is invoked as a child by the loaded-image test, which passed after replacing and recovering a running executable. This separate job does not require the full vcpkg build. The full Tauri/native Windows build remains in progress.

Fault injection stops the actual placement routine and then invokes recovery from the persisted journal. It is not an OS power cut, disk-full simulation or destructive hardware test. The application-level preparation/restart integration has source review and formatting validation locally; the full Tauri/Windows build remains CI work.
